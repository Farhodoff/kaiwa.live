# Sprint 1 security and voice verification

## Findings and changes

- `api/_cors.js` accepted all Vercel preview hostnames and emitted a production origin for untrusted requests. It now validates exact origins, omits CORS permission headers for other origins and preserves `Vary: Origin`. Telegram, SEO, analytics and Vite API handlers use the common rule. Supabase functions `deepseek`, `update-xp` and `send-telegram-notification` share the equivalent Edge rule in `supabase/functions/_shared/cors.ts`. No-Origin requests continue through normal routing and authorization.
- `src/services/AzureSpeechService.ts` used to retry a session 401 as a guest. It now shares a single in-flight request, refreshes the authenticated session once, checks the refreshed account, retries with the new bearer and reports expiry if authorization cannot be restored. A known session becoming absent also stops the flow. Cached Speech tokens are matched to the authorization that requested them. The existing guest service uses the explicit `mode=guest` route and its existing rate and quota checks. A public key never establishes a user identity.
- `src/utils/coachSpeechRecognition.ts`, `src/hooks/useSpeechRecognition.ts` and `src/pages/SpeakingCoachPage.tsx` stop the recognizer and microphone on auth expiry and offer a sign-in action. Provider fallback remains available for service outages.
- `src/lib/consoleFilter.ts` previously expired every readable cookie. The blanket deletion was removed from initialization and callers. Coach, Speech and the DeepSeek API fallback omit cookies for bearer-based requests. Supabase persists app auth through its configured storage adapter. A production browser's cookie sizes, duplicates and ownership still require an authorized profile inspection. Record only byte counts and categories.
- `e2e/speaking-coach-mocked.spec.ts` uses synthetic Chromium audio, simulated browser recognition, a fixture for TTS and a mocked Coach stream. This covers UI, fallback and track lifecycle. Unit tests cover authenticated retry, denied retry, active recognizer cleanup and the sign-in UI. `e2e/azure-speech-integration.spec.ts` separately acquires a real Kaiwa-issued token and uses it to synthesize a short Japanese phrase through Azure.
- `scripts/diagnose-http-431.mjs` probes a real HTTP stack with synthetic Cookie fields, observes whether the handler ran and summarizes response metadata. The local run reached the handler at 0, 4,106 and 8,202 bytes and returned 431 at 18,010 bytes before the handler. That isolates the local Node HTTP parser. The deployment boundary is still unknown.

## Configuration

- Vercel `ALLOWED_ORIGINS` and Supabase Edge `ALLOWED_ORIGINS` accept a comma-separated list of exact HTTPS origins. `https://kaiwa.live` is built in. Add the www host, custom preview origins or an external browser client only if the deployed app actually uses them. Production and preview reject HTTP localhost origins. Vite development permits HTTP loopback. For a local Supabase Edge runtime set `KAIWA_ENV=development`.
- Keep `AZURE_SPEECH_KEY` and `AZURE_SPEECH_REGION` in server configuration. Set `RUN_AZURE_INTEGRATION_TESTS=true`, `AZURE_INTEGRATION_BASE_URL` to an authorized HTTPS staging origin, and inject `AZURE_INTEGRATION_SUPABASE_JWT` for a staging test account through the environment. Then run `npm run test:e2e -- e2e/azure-speech-integration.spec.ts --retries=0`. Keep tracing disabled for this test. It verifies token issuance and synthesis, and needs no microphone.
- Run `node scripts/diagnose-http-431.mjs` for the local parser comparison. For staging set `HTTP_431_TARGET` to the exact HTTPS endpoint and `HTTP_431_AUTHORIZED_ORIGIN` to its origin. Optionally set `HTTP_431_SIZES` to two through six increasing Cookie sizes, beginning at zero and capped at 32 KiB. Without a correlated handler marker or request trace, the rejecting layer remains undetermined. Do not use production session data or production endpoints.

## Before deployment

1. Set the explicit origin lists in Vercel and Supabase, then deploy the changed Edge functions. Verify allowed and unrelated preflights plus independent authentication rejection. Redeploy the server endpoints and frontend together so guest callers use the explicit route.
2. Run the opt-in Azure suite against staging. Compare valid, expired, guest and unavailable-service paths using status codes and redacted request IDs.
3. On an HTTPS staging browser with a physical microphone, deny and grant access in separate runs. Start a Japanese session, speak twice, hear the reply and verify that listening resumes, stopping releases the mic, and history is saved. Repeat start/stop and expire the test account's session during capture. Confirm the sign-in action and the inactive microphone. This requires browser hardware and is separate from synthetic Chromium coverage.
4. If staging produces 431, correlate a baseline request and the failing request across browser, gateway and application telemetry. Adjust a platform header limit or clean an app-owned cookie only after locating the rejecting layer or confirming the offending cookie.
